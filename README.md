# Альфа Хак 2026 — Backend

Backend MVP сервиса персонализированной новостной аналитики для бизнеса. Реализован по зоне ответственности Backend Developer из ТЗ: FastAPI, SQLite, загрузка CSV и RSS, персональная лента, интерфейсы интеграции AI, сохранение инсайтов, вопросы, трассировка и Docker Compose.

## Архитектура

- `backend/main.py` — тонкая ASGI-точка входа.
- `backend/app/` — сборка приложения, CORS/middleware и жизненный цикл старта.
- `backend/api/` — общий API router, зависимости и отдельные route-модули для компаний, новостей, инсайтов и health.
- `backend/models.py`, `backend/database.py` — SQLite-хранилище компаний, новостей, оценок ленты, инсайтов и вопросов.
- `backend/services/company_data.py` — импорт CSV с сохранением неизвестных полей как `null`.
- `backend/services/news.py` — асинхронный RSS-парсер, нормализация текста/дат и исключение точных дубликатов.
- `backend/services/personalization.py` — прозрачный базовый рейтинг, причины и факторы для CEO/CFO.
- `backend/services/insights.py` — кэширование результата и точка подключения `ai.agent.generate_insight` / `ai.agent.answer_question`, если AI-команда добавит модуль.

ML/AI директории пока не предоставлены. Пока они отсутствуют, API честно возвращает базовую оценку и fallback-анализ с пустой позицией банка; результат помечается `validation_status: fallback`. Текст fallback не является банковской аналитикой или результатом LLM. Подключение командных модулей выполняется через указанные Python-функции без изменения HTTP-контракта.

## Запуск

Нужен Docker с Docker Compose.

```bash
docker compose up --build
```

API: <http://localhost:8000>; Swagger: <http://localhost:8000/docs>; OpenAPI: <http://localhost:8000/openapi.json>.

## Тесты

Набор в `test/` использует отдельную временную SQLite-базу и не обращается к реальным RSS-сервисам. Он покрывает health, API компаний и новостей, ранжирование, обновление RSS, создание и кэширование инсайта, вопросы, trace, валидацию запросов, CSV-импорт, нормализацию RSS и дедупликацию.

Запустить тесты в Docker:

```bash
docker compose --profile test run --build --rm tests
```

Собрать HTML coverage-отчёт в `test/coverage_html`:

```bash

```

Откройте `test/coverage_html/index.html` в браузере.

Или установите dev-зависимости и выполните тесты локально:

```bash
pip install -r requirements-dev.txt
python -m pytest
```

Для локального HTML coverage после установки dev-зависимостей используйте:

```bash
python -m pytest --cov=backend --cov-report=html:test/coverage_html
```

Отчёт открывается по пути `test/coverage_html/index.html` и исключён из Git.

## Данные

По умолчанию сервер создаёт три синтетических профиля для демонстрации разных отраслей. Это не реальные компании и не данные организаторов. Чтобы использовать данные кейса, поместите CSV юридических лиц в `data/companies.csv` до первого запуска и задайте `COMPANIES_CSV_PATH`, если файл находится в другом месте. Поддерживаются разделители `,` и `;`, UTF-8 и UTF-8 BOM. Ожидаемые колонки включают `SYNTHETIC_U`, `MAINOKVED_CODE`, `MAINOKVED_NAME`, `REVENUE_COMPANY`, `REGION`, `CITY`, `GROUP_ID`, `CL_PRODUCT_LOA_MARK`, `CL_PRODUCT_LEA_MARK`, `CL_PRODUCT_GAR_MARK`, `FTS_FLAG`, `FTS_COUNTRY_NAME`. Неизвестные значения не домысливаются. CSV исключён из Git.

Профиль загружается при первом запуске пустой БД. Если позже добавить исходный CSV, сбросьте локальную БД и перезапустите приложение, либо выполните импорт в рабочем процессе команды. Платёжные/контрагентские файлы не включены, так как в репозитории отсутствуют сами файлы и их фактическая схема.

## API

Все ответы — JSON. Для трассировки запросов сервер принимает `X-Trace-Id` или генерирует его сам и возвращает в заголовке ответа.

| Метод и путь | Назначение |
|---|---|
| `GET /health` | Проверка приложения и БД |
| `GET /api/companies?q=&limit=` | Список и поиск по синтетическому ID |
| `GET /api/companies/{company_id}?role=ceo\|cfo` | Профиль и полнота данных |
| `GET /api/feed?company_id=&role=ceo\|cfo&limit=` | Персонализированная лента, сортирует backend |
| `GET /api/news/{article_id}?company_id=&role=` | Материал и, опционально, его оценка |
| `POST /api/news/refresh` | Ручная загрузка настроенных RSS источников |
| `POST /api/insights` | Создание или получение сохранённого инсайта |
| `GET /api/insights/{insight_id}` | Сохранённый инсайт |
| `POST /api/insights/{insight_id}/questions` | Контекстный уточняющий вопрос |
| `GET /api/insights/{insight_id}/questions` | История вопросов |
| `GET /api/insights/{insight_id}/trace` | Источники, шаги и статус проверки |

Пример тела `POST /api/insights`:

```json
{"company_id":"SYNTHETIC_U_001","article_id":"<id из /api/feed>","user_role":"cfo"}
```

Пример тела вопроса:

```json
{"question":"Как изменение ставки может повлиять на наши кредиты?"}
```

Ошибки возвращаются в `detail` с машинным `code` и безопасным сообщением; внутренние исключения не показываются клиенту. Основные статусы: 400 — неверный запрос, 403 — неверный токен ручного обновления, 404 — сущность отсутствует, 422 — ошибка схемы, 500 — внутренняя ошибка, 503 — RSS источники недоступны. Ранее сохранённые новости остаются доступны при сбое RSS.

## Интеграция ML/AI

Ожидаемые точки интеграции соответствуют ТЗ: `build_company_profile(company_id, user_role)`, `process_news(article)`, `rank_news(company_profile, articles)`, `generate_insight(company_profile, article, user_question=None)`. В текущем MVP профиль и ранжирование имеют прозрачные backend fallback реализации. При появлении модулей `ml` и `ai` их нужно подключить к этим сервисным границам; API-ключи остаются только на сервере. Повторный `POST /api/insights` для той же компании, новости и роли использует сохранённый анализ, не создавая нового запроса модели.

## Настройка

Скопируйте `.env.example` в `.env`. Параметры: `DATABASE_URL`, `CORS_ORIGINS`, `RSS_FEEDS`, `REQUEST_TIMEOUT_SECONDS`, `MAX_FEED_ITEMS`, `NEWS_REFRESH_TOKEN`, `COMPANIES_CSV_PATH`. Если задан `NEWS_REFRESH_TOKEN`, ручной endpoint обновления требует заголовок `X-Refresh-Token`. Не коммитьте `.env` и ключи моделей.

RSS настроен на ленты Банка России. Сбор происходит вручную по `POST /api/news/refresh`, чтобы не создавать скрытых фоновых задач в демонстрационном MVP. Таймаут, ограничение количества записей, обработка ошибок источника и дедупликация настроены. Разрешённость и доступность внешних источников следует перепроверить перед публичным развёртыванием.

## Ограничения MVP

- CSV-связи физических лиц и платежей не подключены: исходных таблиц нет.
- Персональный скоринг — объяснимый baseline, не финальная ML-модель и не финансовая рекомендация.
- Нет банковских аналитических документов и AI-агента в исходном репозитории; backend не заявляет неподтверждённую позицию банка.
- Корпоративная аутентификация/разграничение доступа не входит в демонстрационную версию.
- Для production следует добавить миграции схемы, ограничение частоты обновлений, планировщик и полноценную авторизацию.

## AI-часть: персонализированная интерпретация новостей

Модуль `ai/` отвечает за то, что сервис объясняет, как новость влияет на конкретную компанию: что произошло, почему это важно, какие есть риски и возможности, что об этом думает Альфа-Банк по своим материалам и где выводы модели.

### Модели

| Модель | Задача | Почему выбрана |
|---|---|---|
| `google/gemma-4-26b-a4b-it` | классификация новости по одной из пяти тем | простая задача, один ярлык, дешевле |
| `z-ai/glm-5.3-flash` | интерпретация, самопроверка, ответы на вопросы | задача повышенной сложности, нужны рассуждения |

Обе модели входят в список разрешённых в приложении 3 ТЗ. Внешних AI-сервисов и готовых агентных систем как основного компонента нет: цикл агента написан вручную.

### Агент (`ai/agent.py`)

1. **План.** Правила без вызова модели. Поиск по материалам банка запускается, только если в тексте новости есть макротермины: ставка, инфляция, ВВП, зарплаты, безработица, курс, кредит, бюджет.
2. **Профиль.** Берётся профиль компании. Поля без данных остаются `null` и перечисляются в `missing_fields`.
3. **Классификация.** Gemma относит новость к одной из тем: `monetary_policy`, `macro_stats`, `industry`, `company_news`, `other`.
4. **Поиск по материалам банка.** Поиск по основам слов (первые пять букв), без векторной базы. Возвращается до трёх фрагментов, в которых совпадают минимум два основы слов с новостью. Каждый фрагмент сохраняет название материала и дату.
5. **Интерпретация.** GLM получает профиль, новость, найденные фрагменты банка и системный промпт с 15 правилами. Ответ возвращается в JSON по схеме `LLMInsight`.
6. **Самопроверка (`ai/validation.py`).** Жёсткие ошибки запускают повтор с замечанием: источник факта не совпадает с новостью, позиция банка не из материалов, неизвестный источник. Мягкие ошибки (факт не найден по словам) только записываются в trace.
7. **Повторы.** Не больше двух повторов после первой попытки. Если валидный ответ не получен, агент возвращает ошибку.
8. **Журнал шагов.** Каждый шаг пишется в `agent_trace` со статусом `ok` или `FAIL` и кратким описанием.

Результат сохраняется в `results/agent__{news_id}__{profile}.json`.

### Схема ответа (`ai/schemas.py`)

Модель возвращает: `what_happened`, `facts` (с полем `source`), `assumptions`, `why_important`, `company_factors`, `consequences` (тип `risk` или `opportunity`, поле `confidence`), `next_actions`, `bank_position` (с полем `source_material`), `ai_conclusions`, `data_limitations`.

Сервис добавляет `news_id`, `company_id`, `sources` и `agent_trace`.

Позиция банка хранится только в `bank_position`, и только с названием материала. Выводы модели идут в `ai_conclusions` и `consequences`. Это разделение задано структурой схемы.

### Уточняющие вопросы (`ai/ask.py`)

Функция `ask(insight, news_text, question)` отвечает только на основе новости и сохранённого инсайта. Если ответа в данных нет, модель пишет об этом и ставит `insufficient_data: true`. После ответа код проверяет числа: цифры, которых нет в данных, попадают в `unverified_numbers`.

### Материалы банка

В `data/bank_analytics/` лежат три PDF Центра макроэкономического анализа Альфа-Банка: ключевая ставка от 11.09.2026, макростатистика 1П26 и 7М26. Там же файл `notes.md` с выводами, датами и короткими цитатами.

Фрагменты для поиска сейчас заданы вручную в `ai/test_data.py` (`BANK_FRAGMENTS`). Автоматического извлечения текста из PDF пока нет.

### Результаты проверки

**Персонализация.** Для новости о ставке 14,0% профиль с кредитами получил риски по стоимости обслуживания долга. Профиль без кредитов с депозитами получил эффект через спрос и доходность депозитов. Для новости о зарплатах и безработице банк не комментировал событие, поэтому `bank_position` пуст. Это ожидаемый результат.

**Устойчивость.** Два независимых запуска без кэша на одном профиле и одной новости:
- числа и даты в `what_happened` и `bank_position` совпали;
- формулировки различаются («Альфа-Банк ожидает» и «Банк ожидает», «сохранил ключевую ставку» и «сохранил… не изменив стоимость денег в экономике»);
- во втором запуске появилась оценка, которой нет в новости. Правило 15 в этом случае нарушено. Это зафиксировано как известное ограничение.

**Порог крупного бизнеса.** Для компании с выручкой 3 млрд руб. модель не применяет логику крупного бизнеса, но в одном ответе отмечает несоответствие критерию из постановки задачи. На результат это не влияет.

### Бюджет

Журнал `llm_log.csv` за 24–25 октября: вход 41 253 токена, выход 68 390 токенов, всего 109 643 токена. Это нижняя оценка:
- не учтён самый первый тестовый вызов (224 токена), он выполнен до появления журнала;
- кэш не считается: повторные ответы из `cache/llm/` в журнал не попадают;
- вызовы с обрывом (`finish_reason: length`) оплачиваются полностью и включены в итог.

Общий ключ команды ограничен 500 ₽ в день. Меры контроля расхода:
- ответы с `finish_reason: stop` кэшируются в `cache/llm/`;
- повтор делается только при жёсткой ошибке или обрыве;
- тестовые запуски выполняются по необходимости, а не в цикле.

### Безопасность

- **Инструменты агента.** Агент использует три инструмента из белого списка: чтение профиля компании, классификация новости, поиск по локальным материалам банка. Выхода в интернет, записи в базу данных и отправки сообщений у агента нет.
- **Ключи.** `LLM_API_KEY` и `LLM_BASE_URL` хранятся в `.env`, который исключён из Git. В коде ключей нет.
- **Журналирование.** Каждый вызов модели пишется в `llm_log.csv`: модель, токены, статус, `finish_reason`, метка шага. Тексты запросов и ответов в журнал не попадают. Каждый шаг агента пишется в `agent_trace`.
- **Данные клиентов.** Используются обезличенные идентификаторы и признаки компании. Имена и контакты в промпты не передаются, потому что в исходных данных их нет. Признаки компании уходят провайдеру языковой модели, это осознанный риск прототипа.
- **Границы решения.** Агент не принимает решений за пользователя. Он формирует интерпретацию и предлагает варианты в `next_actions`.

### Ограничения AI-части

- Материалы банка заданы вручную. Поиск по ключевым словам не понимает синонимы: новость без совпадающих основ слов не получит фрагментов.
- Самопроверка сравнивает слова. Она даёт ложные срабатывания на перефразированных фактах (например, `facts[1]` в тестах) и может пропустить смысловую выдумку, сформулированную другими словами.
- Формулировки меняются от запуска к запуску. Правило 15 соблюдается не всегда.
- Тесты проведены на тестовых новостях. Новости из RSS в AI-часть пока не подавались.
- Порог крупного бизнеса (15 млрд руб.) учитывается моделью в тексте, а не как формальное условие.
- Автоматических unit-тестов для `ai/` нет. Проверка выполняется скриптами, их вывод сохранён в `results/` и `llm_log.csv`.

### Интеграция с Backend

Точка входа для генерации инсайта: `ai.agent.run_agent(profile, company_id, news_id, news_text)`, возвращает объект `Insight`. Для вопроса к сохранённому инсайту: `ai.ask.ask(insight, news_text, question)`, возвращает словарь с `answer`, `insufficient_data` и `unverified_numbers`.
